Takeaway

Computational reproducibility specifically requires obtaining the same results using the same data and same code/analysis.

  • Point out that terms like “reproducible” and “replicable” are often used interchangeably in lay conversations, but The Turing Way establishes precise definitions along a 2x2 grid.
  • Walk through each quadrant:
    • Reproducible: Same data + Same code. This is our baseline standard in computational data science.
    • Replicable: Different data + Same pipeline. Tests if the finding holds up in a new sample or dataset.
    • Robust: Same data + Different pipeline. Tests if the finding is an artifact of a specific software package, model choice, or script.
    • Generalisable: Different data + Different pipeline. The gold standard for scientific claims.
  • Remind students: In this course, we focus heavily on the top-left quadrant (Reproducibility) as the foundation for all the others.

Reproducible \(\neq\) Open Data

  • Open Science promotes making data, code, and papers freely available to everyone.
  • Computational Reproducibility focuses on code execution logic, pipeline integrity, and environment preservation.
  • A project with restricted or sensitive data (e.g., medical, commercial) can still be fully reproducible through:
    • Synthetic test datasets.
    • Containerized environments (Docker).
    • Secure, audited execution pipelines.
  • Address a common student misconception: “My dataset has human subjects / proprietary business data, so I can’t make my project reproducible.”
  • Clarify that Open and Reproducible overlap, but are distinct concepts.
  • Explain how to make restricted data projects reproducible:
    1. Provide synthetic or scrambled mock data that mirrors the schema so external users can verify the code runs.
    2. Write deterministic unit tests and containerize the environment.
    3. Ensure that an authorized auditor inside a secure enclave could re-run the exact script and get identical results.

Reproducibility as “Personal Insurance”

Working reproducibly benefits you (and your team) first:

  • Future-proofing: Your primary collaborator six months from now is your future self.
  • Seamless onboarding: New lab members can run existing pipelines without months of reconstruction.
  • Error resilience: Automated pipelines make updating figures or fixing small bugs fast and low-risk.
  • Frame reproducibility not as an altruistic duty for science, but as self-preservation.
  • Ask the class: “Have you ever opened a project you worked on 6 months ago and spent 2 hours trying to remember which script to run first?”
  • Emphasize “Your future self doesn’t reply to emails.” If you don’t document relative paths, dependencies, and execution order today, your future self will suffer.
  • Mention that automated pipelines (like Make or targets in R) allow you to re-render an entire 50-page manuscript or dashboard with one command after updating raw data.

The “Added Advantage”: Credit & Citation

Publishing reproducible workflows directly boosts academic impact:

  • Higher Citations: Papers with public code and data receive demonstrably higher citation rates.
  • Greater Trust: Independent researchers can audit, verify, and build directly on your work.
  • Secondary Outputs: Reusable R packages, Python libraries, and pipelines earn recognition as first-class scientific contributions.
  • Highlight the selfish incentives for doing open/reproducible work: literature consistently shows a “citation advantage” for papers with publicly available code and data repositories.
  • Explain that code repositories (GitHub/Zenodo with DOIs) allow other researchers to cite your tools even if they aren’t citing your specific empirical findings.
  • Trust is currency in science: when readers can inspect your raw scripts and computational pipeline, they treat your findings with far higher confidence.

Barrier: The “Career Tax” & Incentive Gap

  • Publication Bias: Academic hiring, tenure, and grants overwhelmingly reward novel findings over robust software engineering or replication studies.
  • The Time Sink: Documenting code, setting up continuous integration, and containerizing environments takes significant time.
  • Incentive Gap: Without institutional rewards, researchers view reproducible practices as an unrewarded “career tax.”
  • Connect this to real-world career incentives (hiring, tenure, grant funding).
  • Point out the tension: Building a clean, modular, fully tested pipeline takes 2-3x longer than writing a quick “one-off” messy script.
  • If hiring committees only count the number of novel publications on a resume, the researcher who takes shortcuts will publish faster than the researcher who builds reproducible infrastructure.
  • Ask the class: “How do we fix this incentive structure in data science and computational fields?”

Barrier: Resource & Infrastructure Deficits

Reproducibility requires resources that are often underfunded or unevenly distributed:

  • Skills Gap: Training in software engineering (Git, virtual environments, pipelines) is rarely built into scientific curricula.
  • Computing Costs: Heavy computational pipelines (e.g., multi-GPU training) can be financially prohibitive to re-run or audit.
  • Maintenance: Software dependencies drift over time, requiring continuous maintenance to stay executable.
  • Summarize the physical and structural resource barriers:
    1. Knowledge gap: Most domain scientists were never formally taught Git, Docker, or environment isolation—they are self-taught out of necessity.
    2. Financial/Compute gap: Re-running a deep learning model or climate simulation might cost thousands of dollars in cloud computing credits.
    3. Dependency drift: R packages and Python libraries update constantly. A script written in 2020 may fail in 2026 if packages aren’t pinned (renv/uv/conda).
  • Conclude by setting up the transition to the next part of your course: teaching the practical tools (Git, Quarto, environments) that help overcome these exact barriers.

Scenario C

A research group in climate modeling trains a deep learning architecture for 6 days across a cluster of 32 GPUs, costing $15,000 in cloud compute credits.

A peer reviewer asks the team to re-run the entire pipeline with three alternative random seed initializations to prove statistical stability.

The group’s grant budget is exhausted, and their compute allocation has expired.

Describe at least 2 things that the research group can provide to peer reviewers to prove their pipeline is trustworthy.

  1. Intermediate State Archiving: Saving and publishing model checkpoints, raw log outputs, and loss curves on repositories like Zenodo/OSF.

  2. Dry-Run / Toy Pipelines: Providing a fast, low-compute “mock” version of the pipeline using a small synthetic dataset so others can verify the code logic end-to-end in seconds.

  3. Deterministic Sub-sampling: Demonstrating stability on a lightweight, representative subset of the data before scaling up to full GPU clusters.

  4. Environment & Seed Logging: Strictly archiving the exact container image (Docker), fixed random seeds, and hardware specs so that even if others can’t run it now, the execution state is perfectly preserved for the future.
